# 로컬 RAG를 붙여보니 생긴 일

로컬 기반 RAG 엔진을 실제로 붙여보면 생각보다 재미있는 장면이 나온다.  
문서를 업로드하고, 질문을 던지고, citation까지 돌려받는 흐름은 금방 만들어진다. 그런데 막상 품질을 보기 시작하면 "잘 찾는 것"과 "정확히 답하는 것"이 전혀 다른 문제라는 걸 바로 체감하게 된다.

이번에 리빌드한 `min-minisaas-airag`는 대략 이런 구조다.

- 문서 업로드
- Celery worker로 비동기 인덱싱
- 임베딩 생성
- `Qdrant`에 dense vector 저장
- `Elasticsearch`에 lexical/BM25 인덱싱
- 질문 시 hybrid retrieval
- citation과 함께 응답 반환

여기서 가장 신기했던 건, "LLM이 멋지게 써줘서"보다 "임베딩이 의미를 꽤 잘 잡는다"는 부분이었다.

예를 들어 문서에는 이런 문장이 들어 있다.

> 데이터 손실 가능성이 보이면 운영 책임자와 보안 담당자에게 바로 에스컬레이션해야 한다.

그런데 질문은 이렇게 바꿔 던졌다.

> 데이터가 사라질 거 같으면 어떻게 해야 해?

문서에는 `사라지다`라는 표현이 없다. `손실`이라는 표현만 있다.  
그런데도 현재 `airag`는 이 질문에 대해 관련 문장을 찾아냈고, citation까지 함께 돌려줬다.

이 결과는 단순 키워드 매칭만으로 보기 어렵다. 지금 구조에서는 아래 조합이 실제로 개입한다.

- `LlamaIndex`
  - 흐름과 설정을 묶는 orchestration 레이어
- `OllamaEmbedding(nomic-embed-text)`
  - 문서와 질문을 벡터로 바꾸는 임베딩 모델
- `Qdrant`
  - dense retrieval 저장소
- `Elasticsearch`
  - keyword/BM25 검색 저장소
- `qwen2.5:7b`
  - 로컬 LLM 설정은 되어 있지만, 현재 성공 사례의 핵심은 생성보다 retrieval 쪽이다

즉 이번 사례의 핵심은 "LLM이 잘 썼다"보다 "임베딩 검색이 의미를 꽤 잘 잡았다"에 가깝다.

## 의외로 잘 되는 것

현재 엔진이 비교적 잘 처리하는 건 설명문, 운영 가이드, 정책 문서, FAQ 같은 문장형 텍스트다.

예를 들어 이런 문서가 있다고 하자.

- 장애 대응 가이드
- P1 장애 시 1차 대응 절차
- 고객 공지 원칙
- 에스컬레이션 기준

이런 문서를 넣고 다음처럼 물으면 꽤 자연스럽게 답이 나온다.

- `P1 장애가 발생하면 가장 먼저 무엇을 해야 해?`
- `데이터가 사라질 거 같으면 어떻게 해야 해?`

실제로 현재 QA 시나리오에서도 이 유형은 잘 통과한다.

## 바로 드러나는 한계

반대로 표 데이터나 숫자 질의는 생각보다 어렵다.

예를 들어 축구 순위표처럼 이런 데이터를 넣으면:

```text
2003;1;Cruzeiro/MG;100;31;7;8;55;102;47;46;72.50%
2003;2;Santos/SP;87;25;12;9;33;93;60;46;63.00%
2003;3;Sao Paulo/SP;78;22;12;12;14;81;67;46;56.50%
```

다음 같은 질문은 retrieval은 되지만 답 품질이 불안정하다.

- `2003년 1위 팀은?`
- `Corinthians/SP의 순위와 승점은?`
- `goals against가 47인 팀은?`

왜 이런 일이 생길까.

- 지금 chunking이 아직 단순 문자 길이 기반이다
- 표의 여러 행이 한 chunk에 섞인다
- retrieval은 정답 근처를 잘 찾지만, 답변은 정답 한 줄만 뽑지 못하고 주변 행까지 같이 보여준다

즉 현재 단계는 "관련된 건 찾는데, 정확한 row 하나만 딱 집어서 대답하는 능력은 아직 약한 상태"라고 보는 게 맞다.

## 그래서 느낀 결론

RAG는 생각보다 빨리 돌아간다.  
하지만 "문서를 넣으면 알아서 다 해준다"는 말과는 거리가 있다.

정확히는 이렇게 정리하는 게 맞다.

- 설명문 기반 검색과 질의응답은 꽤 빠르게 쓸 만해진다
- 의미적으로 가까운 표현도 어느 정도 잡아낸다
- 하지만 표, 영수증, 청구서, 이미지 같은 문서는 별도 전략이 필요하다
- retrieval과 answer synthesis는 다른 문제다

특히 고객이 실제로 던지는 문서는 더 복잡하다.

- `docx`
- `xlsx`
- `pptx`
- `hwp`
- 이미지
- 스캔 PDF
- 영수증, 계약서, 인보이스

이런 문서까지 잘 처리하려면 단순 RAG만으로는 부족하다.

- OCR
- 문서 타입 분류
- 표 row-aware chunking
- 메타데이터 추출
- structured retrieval
- 필요 시 extractor나 reranker

까지 붙어야 실무형 서비스가 된다.

## 한 줄 요약

이번에 얻은 가장 현실적인 결론은 이거다.

> 로컬 RAG도 생각보다 의미 검색은 잘한다.  
> 다만 "정확한 정답 한 줄"을 안정적으로 뽑으려면 문서 타입별 ingestion과 structured extraction이 꼭 필요하다.

그래도 재미있는 건, 막연히 "로컬 모델은 다 별로겠지"라고 생각했는데 실제로 붙여보니 retrieval 품질은 생각보다 꽤 인상적이었다는 점이다.
